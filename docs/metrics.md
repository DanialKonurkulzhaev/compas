## Автоматические проверки `test_metriks.py`

Из активированной `.venv` в корне Compas:

```powershell
python -m pytest tests/test_metriks.py -v -o addopts=""
```

По умолчанию выполняются 13 изолированных проверок: ограничение пула и восстановление после его исчерпания, измерение длительности и идентификаторы запросов, readiness при имитации сбоя БД и после восстановления, откат незавершённой транзакции, повторное использование токена другим HTTP-клиентом, добавление/изменение/удаление теста администратором, ограничения связей в БД, хеширование, целостность шифротекста, отказ для просроченных/refresh-токенов, запрет редактирования обычному пользователю и отсутствие учётных данных в журнале запросов.

Две инфраструктурные проверки по умолчанию пропускаются (`SKIPPED`). Для измерения 100 GET-запросов с 10 одновременными клиентами запустите Compas на тестовом стенде и выполните:

```powershell
$env:COMPAS_METRICS_URL = "http://127.0.0.1:8001"
python -m pytest tests/test_metriks.py -k live_get_workload -s -v -o addopts=""
Remove-Item Env:COMPAS_METRICS_URL
```

Отчёт выводит p50/p95, запросы в секунду и HTTP-статусы. Проверка требует 100 ответов HTTP 200, но не устанавливает выдуманный порог скорости.

Для пробного восстановления укажите существующий PostgreSQL-дамп, созданный `scripts/backup.py create`:

```powershell
$env:COMPAS_METRICS_BACKUP = "C:\absolute\path\compas.dump"
python -m pytest tests/test_metriks.py -k postgres_backup -s -v -o addopts=""
Remove-Item Env:COMPAS_METRICS_BACKUP
```

Проверка требует Docker и работающего `db` из Compose. Создаётся отдельная БД `compas_restore_*`; рабочая БД не очищается. Новая БД остаётся для осмотра. Проверка подтверждает успешное восстановление архива, но не заменяет сравнение всей истории и расшифровки результатов.

Для XML-отчёта добавьте `--junitxml=metriks-report.xml`. Наличие этих тестов не означает полного выполнения всех шести метрик: сравнение 1/2/4 процессов, EXPLAIN ANALYZE на PostgreSQL, нагрузка на запись, перезапуск Docker-хоста, HTTPS и аудит безопасности остаются отдельными проверками. Изолированные проверки используют SQLite и подменённый сбой соединения; они не измеряют реальную доступность PostgreSQL.

## Нагрузочный скрипт

Запускайте на стенде с заполненным каталогом. Пример:

```powershell
python scripts/load.py --requests 500 --concurrency 10 --output load-results-10.json
python scripts/load.py --requests 1000 --concurrency 30 --output load-results-30.json
docker compose stats --no-stream
```

Клиент выполняет только GET и выводит throughput, p50, p95 и статусы HTTP. По умолчанию проверяется `/tests`. Для защищённой ручки задайте в окружении `COMPAS_ACCESS_TOKEN`; токен не записывается в отчёт. Каталог не воспроизводит дорогой расчёт тестов или массовую запись: эти сценарии необходимо отдельно нагрузить на одноразовой БД с тестовыми аккаунтами.

## Резервное копирование и восстановление

```powershell
python scripts/backup.py create
python scripts/backup.py verify backups/ИМЯ.dump
python scripts/backup.py restore-check backups/ИМЯ.dump
```

`verify` проверяет только структуру архива. `restore-check` создаёт БД со случайным именем `compas_restore_*`, восстанавливает дамп одной транзакцией и выводит ревизию и количества строк. Рабочую БД он не очищает. После проверки отдельно сверьте результаты, вход, алерты и расшифровку с тем же DATA_ENCRYPTION_KEY. Отдельная тестовая БД остаётся для осмотра.

Резервные копии БД и аватаров необходимо хранить вне Docker-хоста; шифровальный ключ отдельно. Скрипт копирует только БД; том `compas_avatars` архивируется отдельно. Согласуйте частоту резервирования и срок хранения, затем подключите расписание на сервере. Автоматическое расписание в этом проекте пока не установлено. После каждого изменения схемы повторите проверку восстановления.

## Миграции

`compas_0001` — собственная начальная ревизия для новой БД. История миграций «Одеяло» сюда не переносится. Для обновления:

```powershell
alembic revision --autogenerate -m "describe change"
# Проверить полученный SQL и совместимость на копии БД.
alembic upgrade head
```

Не подключайте старый том PostgreSQL другого major-релиза. Перенос реальных пользователей и истории требует отдельного согласованного экспорта/импорта, а не подключения production-тома к новому проекту.

## Ограничения

Проект наследует формулы и пороги существующего каталога. Их методическая проверка — отдельная задача. Технические тесты подтверждают сохранение поведения, а не клиническую валидность. Система не содержит ИИ. Работа с данными не проверена на серверной БД и не является полной сертификацией безопасности.
